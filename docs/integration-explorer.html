How to retrieve the information that is still missing on the Salesforce records, using a new API on the middleware that reads the catalog JSON. Based on the audit of all 1,155 production webhook calls (2026-07-14): the webhook now captures everything it sends, so what remains comes from three sources — middleware catalog API, webhook replay, and SecuTix setup.

Full node structure, ready to hand to the middleware team: the request plus a resolved response for all 10 real products (every family, sale periods, advantages, cross-sells, fixed-seat subjects, tariff grids) and the found:false case.

1 · The middleware API to build — POST /catalog/products/resolve

One batched endpoint. Salesforce sends up to 50 product ids; the middleware joins the catalog JSON (the 109 relations mapped in the “Relations graph” tab) and returns everything already resolved — Salesforce never walks the catalog tree.

// request — batch of external product ids (max 50) { "productIds": [10228636435680, 10228636435676, 10228682346339, 10228636523446, 10228683831060, 10228680140505, 10228676772860, 10228687124788, 10228656709105, 10228635491731, 10228683831063] }

// response — complete worked example from the 2026-07-17 export: ALL 10 products from the Resolved examples tab (incl. salePeriods, fixed-seat subjects, tariff dependency rules) + the found:false case. Click any node to expand/collapse.

Rules: flatten translations[] to one it/en string per name (most of the payload bulk) · keep each object shallow (id, code, name + a few business fields) · idempotent, so Salesforce can retry freely · cap at 50 ids per request.
