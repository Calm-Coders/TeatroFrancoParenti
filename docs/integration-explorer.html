How to retrieve the information that is still missing on the Salesforce records, using a new API on the middleware that reads the catalog JSON. Based on the audit of all 1,155 production webhook calls (2026-07-14): the webhook now captures everything it sends, so what remains comes from three sources — middleware catalog API, webhook replay, and SecuTix setup.

1 · What is missing on the records today
webhook replay

New fields empty on the 971 prod records

Season_Id__c, Contact_Product_Links__c, Exchangeable__c… only fill when a product is re-sent. Old records keep them blank.

How: ask the middleware to trigger a full inventory resync — the upsert by Inventory_Id__c makes replay safe and idempotent.
catalog API

productTypeId arrives null

Only 2 of 1,324 payloads carried it. The product type lives in the catalog (seasons[].productTypes, 18 entries), not in the webhook.

How: resolve per product via /catalog/products/resolve and write Product_Type_Id__c + name.
catalog API

Tariff & venue names

Performance__c stores prices/seat grids with bare ids (audSubCatId, seatCatId, priceLevelId, physical/logicalConfigurationId, siteCode).

How: the resolve response carries small lookup lists (tariff legend, venue, rate types) — ~100 entries total across the whole catalog.
catalog API

22 products > 6 MB never ingested

Payloads over Apex's 6 MB string limit failed on every retry, and the log body is null so they are untraceable from Salesforce.

How: middleware sends those products with event.performances split into chunks (e.g. 200 performances per call), or strips prices[] and lets the resolve API serve them on demand.
SecuTix setup

ticketModelId is a dangling id

No ticketModels[] collection exists in the catalog — ticket models are institution-level configuration.

How: middleware keeps a tiny static id→name map fetched once from SecuTix setup (only a handful of distinct ids exist, e.g. 634688343).
catalog API

Season names & dates

Season_Id__c now stores the id (e.g. 10228683117776) but Salesforce has nothing to display for it.

How: include season {id, code, name, start, end} in every resolve response — or sync the 2-row season list once per day.
2 · The middleware API to build — POST /catalog/products/resolve

One batched endpoint. Salesforce sends up to 50 product ids; the middleware joins the catalog JSON (the 109 relations mapped in the “Relations graph” tab) and returns everything already resolved — Salesforce never walks the catalog tree.

// request — batch of external product ids (max 50) { "productIds": [10228688884880, 10228683111111] } // response — one entry per product, every raw id resolved to an object { "products": [{ "productId": 10228688884880, "found": true, "season": { "id": 10228683117776, "code": "2627", "name": "STAGIONE 26-27", "start": "2026-06-01", "end": "2027-07-31" }, "productType": { "id": …, "code": …, "name": … }, "audienceSubCategories": [ { "id": 10228683504635, "code": "IN", "name": "Intero", "kind": "PAYING" } ], "seatCategories": [ { "id": 10228687283420, "code": "TRIB", "name": "Tribuna" } ], "priceLevels": [ { "id": 10228687469865, "code": "Abbonato" } ], "performances": [{ "performanceId": …, "site": { "code": …, "name": …, "town": … }, "space": { "code": …, "name": … }, "physicalConfiguration": { "id": …, "name": …, "securityGauge": … }, "rateType": { "id": …, "code": …, "name": … } }] }, { "productId": 10228683111111, "found": false }] // unknown id ≠ error — keeps the batch alive }

Rules: flatten translations[] to one it/en string per name (most of the payload bulk) · keep each object shallow (id, code, name + a few business fields) · idempotent, so Salesforce can retry freely · cap at 50 ids per request.

4 · Backfilling the 971 existing records (deduped 2026-07-14)
option A · recommended first

Full webhook resync — keep the records

Middleware re-sends every product through the existing /v1/inventories endpoint. The atomic upsert on the now-unique Inventory_Id__c rewrites all 58 fields in place and creates the child records (Inventory_Event__c, Performance__c…) — a delete is not needed to get a clean mapping.

Covers: everything the webhook carries, with zero side effects. Doesn't cover: productType, tariff/venue names, ticket models.
option A′ · delete + retrigger

Clean slate — only with a re-link step

Deleting Inventory__c first purges obsolete products, but 294,379 Order_Operation_Data__c records hold Inventory__c lookups (SetNull on delete) — an inventory resync does not restore them; they are only linked when an order is ingested.

If you delete: after the resync, run a one-off re-link batch matching Order_Operation_Data__c.Product_Id__c → Inventory__c.Inventory_Id__c (same logic the Order API already uses). Access_Control__c is safe today (0 linked).
option B · after A

Batch enrichment sweep

A one-off Batchable iterates Inventory__c where the enrichment fields are empty, calling /catalog/products/resolve in batches of 50 (≈20 callouts for 971 records) and writing the resolved names/ids back.

Covers: the catalog-only data. Reuses the same Queueable/service class as the live flow — write it once.
5 · Decision to make

Where should the resolved catalog entities live? Option 1 — fields on Inventory__c/Performance__c (e.g. Product_Type_Name__c, Site_Name__c): simplest, good for reports, denormalized. Option 2 — small reference objects (Product_Type__c, Rate_Type__c, Site__c… with external ids, converted to lookups): proper model, clickable in the UI, ~100 records total, slightly more work. If the catalog changes rarely, option 2 with a daily sync is the cleaner long-term shape; option 1 ships faster. Both reuse the same middleware endpoint.
